# 从第一版走到业务 Demo

## 已搭建的基础

本地条目检索、DeepSeek 客户端、带引用 RAG、CLI/API、裁量事实检查、PDF 待整理提取、来源和版本字段、离线回归题集。

## 接下来按顺序做

| 阶段 | 具体工作 | 验收方式 |
| --- | --- | --- |
| 1. 接通模型 | 本地填写 Key，先跑 `chat` 再跑 `ask` | 正常解释、空回复/错误返回可识别；原文与页码可核对 |
| 2. 补齐一个事项 | 确认上传文件版本，补齐法条全文、裁量实施办法和适用地域 | 原文、时间、版本、边界解释均有来源 |
| 3. 可复现裁量 | 将通过核验的条件整理成规则，明确定义以上/以下、例外和必要事实 | 测试 19.9999/20/20.0001、39.9999/40/40.0001 及例外情况 |
| 4. 扩大检索 | 增加几个相关事项；在基线评测中比较 BM25、Embedding、混合检索 | 分开测召回、排序、范围外拒答和错误版本 |
| 5. 单智能体 | 包装四个现有工具为 AgentScope 工具，加入最大调用次数和超时 | 能展示工具输入输出；缺事实能补问并恢复流程 |
| 6. 多轮和资料更新 | SQLite 保存会话/案件；原始文件 → 候选条款 → 核验 → 索引版本发布 | 新案件不串用旧事实；新版本可回滚、历史版本可查 |
| 7. 展示界面 | 增加 Streamlit 或独立前端，展示答案、引用和待补事实 | 能演示命中、缺事实、范围外、数据更新四种场景 |

先保持当前模块边界。后续添加 Qdrant 或 AgentScope 时，不需要重写来源校验和事实检查。

## 评测建议

当前 20 条题是开发回归题，只有一个事项。增加语料时把“同一案件的不同问法”放在同一集合，分别保留开发集和验收集。

记录：候选依据是否找全、排序是否正确、是否误用其他版本、解释是否受原文支持、缺事实是否追问、规则边界是否正确。真实问题的标准答案应由熟悉业务的人核对，避免用模型自己的答案作为唯一标准。

摄像头和无人机发现的事件可在更后面作为线索来源接入；先把文字事实到依据和规则的流程做稳。
